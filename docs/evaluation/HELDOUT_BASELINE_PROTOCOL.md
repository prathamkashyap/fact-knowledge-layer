# Held-Out Deterministic Baseline Protocol

**Frozen before extraction.** This protocol applies only to the two PDFs and 50 independently annotated facts in `heldout_gold.json` at gold-set commit `979563f9af7bb054fd24c856010998a9be989bdd`. The frozen extractor baseline is `d9c68bd424883a09107b7507e348107e9f4fbc41`.

## Scope and denominator

The annotations sample financial highlights and segment metrics from the Rolls-Royce annual report and selected indicators from the IMF table. They are not an exhaustive census of claims in either full PDF. The primary metric is **sampled-gold recall**: distinct annotated facts recovered divided by the annotated facts for that document (Rolls-Royce: 27; IMF: 23) and overall (50). Report raw extractor candidates separately from the pipeline's final validated, deduplicated facts used for matching.

Do not treat unmatched predictions as false positives. Formal precision, F1, and false-positive counts are **not yet defensible** under this annotation scope. Keep unmatched predictions for later source adjudication.

## Candidate and match rules

1. Score each document independently. A match must be supported by a final fact retained by the existing pipeline for that same input PDF. Its evidence page is the 1-based physical PDF page. The raw pre-normalization facts emitted by the page extractor are retained and counted, but a fact rejected by evidence validation or removed by the existing pipeline is not a recovered gold fact.
2. Match one prediction to at most one gold fact and one gold fact to at most one prediction. A gold fact is recovered only when every required dimension below agrees. No fuzzy score, nearest-value choice, or manual correction is allowed.
3. **Entity:** casefold and collapse whitespace; use `canonicalize_entity` for its existing legal-suffix and entity normalization. Only exact issuer aliases within the source document are equivalent: Rolls-Royce / Rolls Royce / Rolls-Royce Holdings plc; and UK / United Kingdom for the IMF document. The IMF is the publisher, not the subject entity. Segment identities (Civil Aerospace, Defence, Power Systems) must agree when the gold evidence identifies one; an issuer-level prediction with no matching segment attribution is ambiguous.
4. **Claim type:** casefold, collapse whitespace, and ignore punctuation-only differences in the predicate. `canonicalize_predicate` may identify a broad metric family, but is not sufficient by itself: preserve modifiers and subtypes such as real versus nominal, period-average versus end-period, annual average versus point-in-time, volume growth, and gross versus net. Underlying and statutory measures are distinct claim types. A candidate must explicitly support the gold's underlying/statutory basis through its predicate, qualifiers, or evidence; missing basis is ambiguous, not an assumed match.
5. **Value and unit:** parse numeric strings with decimal arithmetic, allowing grouping commas and only presentation marks consistent with the recorded unit (for example `£`, `%`, `m`, `bn`, or `p`). Require exact numeric equality after formatting normalization; do not use a tolerance. Units must agree after case/space normalization and only unambiguous aliases (for example `%` and `percent`). Do not convert across currencies. Any magnitude conversion is allowed only within the same explicit currency and only by an exact unit scale. Do not use the production normalizer's generic `million` conversion for GBP: it canonicalizes million units to INR million.
6. **Reporting period and effective date:** preserve the full period and its granularity. Use `normalize_period` only when both values resolve to the same specific period type without losing information; otherwise compare casefolded, whitespace-normalized text. Do not equate a calendar year with a year-ended period, an end-period stock with an annual average, or a date with a year merely because a normalizer extracts the same year. `as_of` is a separate dimension and must agree when present in gold.
7. **Actual versus forecast:** derive status from explicit projection/forecast markers in the gold's qualifiers/reporting basis and the prediction's qualifiers/evidence. A projected gold fact requires a projected candidate. An explicit status conflict is not a match. If the candidate lacks enough evidence to distinguish a projected fact from a historical one, mark it ambiguous and do not count it as recovered.
8. **Scope and basis:** scope must agree when gold specifies it (`consolidated` or `United Kingdom`). Preserve explicit reporting distinctions from the gold's `reporting_basis`, including underlying/statutory, segment attribution, period-average/end-period, annual average, and the ILO measure. Do not infer a missing distinction from a matching number.
9. **Evidence:** the candidate must cite the same physical PDF page as the gold's `evidence.pdf_page_index`, and its evidence text must contain the quoted value after the same safe formatting normalization used above. Page/evidence differences do not create different facts, but incorrect or insufficient grounding prevents a gold match.

## Duplicates, conflicts, and ambiguity

Preserve every raw candidate. Group exact repeated claims using the dimensions above; duplicates count once toward recovered gold facts, are listed as duplicate predictions, and never increase recall. If multiple predictions could match the same gold fact, assign at most one using stable output order and report the rest as duplicates only when all claim dimensions agree. Different values or incompatible bases are conflicts, not duplicates; record them separately. If a candidate can map to multiple gold facts after applying all dimensions, label it ambiguous and do not count it as a match. Unmatched or ambiguous predictions remain unadjudicated, not false positives.

For each document, report raw pre-normalization candidate count, final validated/deduplicated fact count, distinct gold facts matched, unmatched gold IDs, duplicate/ambiguous/conflicting predictions, and sampled-gold recall. Report the same overall recall over all 50 facts. Keep the gold file byte-for-byte unchanged.

## Execution boundary

Use `app.pipeline.process_document_pipeline` once per active PDF with `provider=None`, `reasoning_mode="heuristic"`, and an explicitly supplied isolated SQLite database. This is the existing deterministic offline path. Do not invoke `scripts/evaluate.py` for these documents, use the API upload endpoint, call an external provider, or change thresholds/rules. Clear the in-memory PDF parse cache before each document. Preserve raw extractor facts and final pipeline facts with source hashes and run metadata; keep temporary database/cache/output files outside the original checkout.
